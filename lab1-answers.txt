In your own words, describe what Lab1 was about: Describe the various components that you implemented and how they work.
 This part needs to demonstrate your understanding of the lab! If your description looks like a copy paste of the
 instructions or a copy-paste of the provided documentation you will lose points.
- In Lab 1, we developed components of SimpleDB to handle a basic query SELECT * FROM some_data_file.
- For BufferPool.java, our buffer pool can only store up to numPages. When exceeding this, we would throw an exception
instead of using an LRU policy. Compared to our homework, we had to consider a LRU eviction policy rather than throwing
an exception.
- seqScan() involved reading through each tuple in a table with methods like next() and open(). Utilizing iterators was
essential in this process, helping us traverse through DBFiles. The database file is retrieved from the catalog, with
iterators helping it browse through the table’s contents for seqScan(). The iterator shows how pages are fetched on at
a time from the buffer pool, stored in memory, enabling the heap file’s cursor to access tuples.
- To determine whether a slot is used/unused, we used the header bitmap to determine the slot usage. In getPageDate(),
unused slots have their byte arrays filled with zeros.
- A table is stored in a HeapFile, which will contain multiple HeapPages. Each HeapPage is grabbed from disk and stored
in the BufferPool as a HashMap mapping PageId to Page. If we had a page that is not in the bufferpool, we would add them
in from the disk using the getPage() method in BufferPool. Each HeapPage has a specific amount of tuples in them which
can be accessed with an iterator, it also consists of a header with unused/used bitmaps and tuples, and each table can
span over multiple heapPages, so when iterating through tuples, we can iterate over the page, and if there is no more
after, we will move onto the next page with the tuples left over.

Describe any design decisions you made. These may be minimal for Lab 1.
- We utilized a HashMap that mapped PageId to Page to store pages in bufferpool because fetching a page through its
PageId is a frequent action and HashMap provides O(1) fetch time.
- We implemented an iterator using an iterator over pages (tupleIterator). We also used a counter (pageNumber) to keep
track of the current pages.
- For catalog we opted HashMaps to map relationships with id, tableName, DBFile, tupleDesc, and primary key.
